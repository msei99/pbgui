# PBCoinData Service


PBCoinData is a background service that fetches CoinMarketCap (CMC) listings and metadata and builds exchange symbol mappings. These mappings power the dynamic coin filter logic used by PBRun (`ignored_coins.json` / `approved_coins.json`).

Hyperliquid HIP-3 availability includes every DEX marked active in the local mapping, including PARA and MKTS. Editor coin lists, Dynamic Ignore, Balance Calculator and the local Market Data settings snapshot retain the usual active/swap/linear and open-interest checks. HIP-3 ticker names retain their full suffixes, such as `PARA-FOOUSD`. TradFi stock routing remains specific to XYZ.

Editor status checks use the same mapping identities as the picker. Additional HIP-3 DEX aliases are confirmed from the selected Hyperliquid mapping, so a full ticker such as `NEWDEX-FOODAI` remains valid instead of being shortened to `NEWDEX-FOO`. Unconfirmed aliases cannot select a different ticker by dropping a quote-like ending.

## What PBCoinData does

PBCoinData runs a daemon loop (60-second cycle) that:

- Fetches CMC listings (rank, market cap, volume, tags) on a configurable schedule
- Fetches CMC metadata — primarily the `notice` field (delisting/migration warnings used by dynamic filters)
- Builds per-exchange symbol mappings (`data/coindata/{exchange}/mapping.json`) for V7-supported exchanges (binance, bybit, bitget, gateio, hyperliquid, kucoin, okx), limited to known running consumers on explicit slaves as described below
- Detects copy-trading symbols per exchange (bybit: from CCXT market data; binance/bitget: via authenticated API with automatic user discovery)
- Resolves duplicate CMC symbols (e.g. HOT, ACT) via price-based disambiguation using exchange ticker prices
- Runs TradFi sync for Hyperliquid HIP-3 stock-perp symbols (master-only for web scraping; automatic slave cycles require Hyperliquid in the exchange selection)
- Runs a self-heal cycle that automatically retries exchanges with failed mappings (exponential backoff)
- Writes service logs to `data/logs/PBCoinData.log`

## Configuration

Click the PBCoinData card on the Services overview. Credentials are managed in **Pool**; non-secret schedules remain in **Settings**.

### CMC pool

Use **Pool -> Add Key** to add one or more CMC keys. Secrets are stored in the owner-only credential vault and are never returned by status APIs or reveal controls.

- **Imported / externally used** keys are allowed and participate in local fair selection.
- Mark **Shared quota** when the same provider quota is shared outside this PBGui entry.
- Cluster Sync distributes sealed generations; do not put a CMC key in `pbgui.ini` or configure one per VPS.
- Leases coordinate usage when available, but are best effort. If leasing is unavailable, each node falls back to its local soft budget.
- A provider `429` cools down that key and the request can fail over to another eligible key. Invalid, disabled, exhausted, cooling, or conflicted keys are skipped.
- **Rotate** is optional and replaces the selected key with a new immutable generation. **Disable** keeps its history; **Delete** publishes a tombstone.

PBCoinData can run without a ready pool to refresh exchange-side mapping inputs, but CMC listings and metadata fetches are skipped until at least one active key is materialized.

### Scheduling

| Setting | Default | Description |
|---|---|---|
| `Fetch Interval` | `24` | How often CMC listings are re-fetched (hours) |
| `Fetch Limit` | `5000` | Max symbols fetched per CMC call |
| `Metadata Interval` | `1` | CMC metadata refresh (days) |
| `Mapping Interval` | `24` | Exchange mapping rebuild interval (hours) |

Free Basic plans are sufficient for most setups. The status bar and Pool tab show readiness, active-key count, health, generations, local usage, provider remaining credits when reported, cooldowns, failures, and secret-free lease statistics.

## Self-heal cycle

On an explicitly configured slave, the automatic daemon refreshes only exchanges used by running local PB7 bots with Dynamic Ignore enabled. It checks every matching process, compares `config.json` and `config_run.json`, and resolves `live.user` through the local PB7 account projection. Only exchange names are retained in the selection; credentials are never included in lifecycle metadata or logs. Missing/unreadable accounts, differing desired/runtime values, unknown processes or unsupported exchanges retain full exchange coverage. A known active consumer still prevents unloading even when exchange coverage is incomplete.

The same selection applies to self-heal and scheduled market, copy-trading, mapping and price requests. A newly needed exchange with an expired mapping interval is refreshed in the next daemon cycle, without shifting the existing global schedule; fresh mappings can be reused. Retry backoff remains per exchange when consumers leave and return. Shared CMC listings/metadata keep their existing intervals. Masters and direct Coin Data UI jobs retain full exchange access, including individual refreshes.

On explicitly configured slaves with automatic service healing enabled, an owned daemon is unloaded only after confirming that no running PB7 Dynamic Ignore consumer needs it. Desired and runtime configuration are both checked; ambiguous process or configuration state is observation only. With a ready CMC pool, a running consumer permits automatic recovery. Masters retain credential-based behavior. PB8 live bots have no DynamicIgnore daemon dependency. See **System → VPS Monitor → Services** for the separate `idle` status, actual process state and demand reason. Manual service actions use the separate action-specific authorization described below.

The local monitor agent alone controls installed systemd units in its regular 60-second cycle. For legacy operation, an initialized current PBRun owns an exclusive controller lease and reconciles in its existing five-second maintenance cycle, including recovery after the first consumer starts. If that lease is free, the local monitor agent can acquire it for one fallback cycle. A PBRun PID alone is not recovery authority. An installed unit or an unconfirmed manager prevents automatic legacy starts. No additional persistent controller process is created.

Legacy unloading requires a verified recovery controller and exact ownership of this checkout's Python process: UID, script position, resolved script, working directory, PID and start time must match. Unknown or foreign identities are never signalled or treated as stopped. A standalone legacy daemon without a verified PBRun controller or agent fallback retains its waiting idle loop, because automatic recovery is not assured. Missing or unrecognized roles do not authorize unloading.

The manager check uses current evidence within a shared five-second budget (at most three seconds for systemctl). An online `not-found` result permits legacy operation only when the unit is inactive, has PID 0 and has no job. Without a reachable user manager, legacy operation requires a positive offline proof: compiled and configured SYSTEMD_UNIT_PATH/XDG/home/system/runtime search paths must be determinable and readable, with no relevant unit, alias, mask or transient/generator artifact. Complete process, namespace, cgroup and runtime-socket evidence must exclude an own user manager. Bus failure alone never authorizes a start. Missing path-discovery tools, inaccessible metadata, a live manager or uncertain container/process visibility remain unknown; standalone or unverifiable environments are not fully covered. Manager loss after unloading can recover automatically after a fresh complete offline proof. A rejected PBCoinData action does not prevent subsequent services in the same starter batch from being processed; the batch still exits with an error.

Actual legacy spawn/readiness failures use a separate shared start backoff: 60 seconds after the first failure, then exponentially up to 1800 seconds. PBRun, agent fallback and replacement controllers share private atomic UTC wall-clock state in `data/state/pbcoindata-start.json`, serialized by the action locks. IDLE and controller changes retain the wait. Exact successful automatic startup clears it; a failed reset write does not kill an already healthy process. Explicitly authorized manual start/restart may bypass the wait. Success preserves the previous retry-file bytes; an actual start failure still updates the shared failure state. Unknown manager/process state and lock conflicts do not count as spawn failures. Corrupt data or clock corrections are repaired with one persisted 60-second minimum wait; unsafe persistence defers automatic starts. An interrupted attempt retains a conservative deadline. This does not change the exchange mapping backoff below.

Manual **Restart** remains available while PBRun holds the controller lease; it uses the shared action locks. It does not pin an idle daemon in memory: the next confirmed IDLE controller cycle can unload it again. Legacy start readiness is bounded to ten seconds; stop waits up to ten seconds after SIGTERM, then up to two seconds after SIGKILL of the same reverified owned process. Unconfirmed exit blocks replacement. Systemd retains its separate bounded stop/status checks; an unfinished transition is observed before another start. Brief intermediate states can pass between monitor updates.

PBRun can bootstrap a missing exchange mapping before the first Dynamic Ignore bot starts, without waiting for the unloaded daemon. A ready CMC pool is still required for that startup path. Full unloading releases the PBCoinData process; no specific RAM reduction is guaranteed or measured here.

Failed catch-up refreshes do not count as fresh mappings. PBCoinData retains their exchange-specific retry state even if the failed attempt already rewrote a mapping file or its consumer temporarily leaves the selection. Retries wait 1 hour after the first failure, then 2, 4, 8, 16 and at most 24 hours after subsequent failures. A scheduled global cycle also respects that wait. A successful refresh clears the retry state; catch-up retries do not move the global mapping schedule. The log shows `Catch-up mapping failed`, followed by `Self-heal mapping trigger` and a success/failure result when the retry is due.

### Guard ownership and legacy transition

Manual start visibility uses typed own namespace descriptors (`NS_GET_NSTYPE`), initial PID/user identity and complete UID mapping. Authenticated procfs mountinfo descriptors for self and PID 1 remain open together while complete mount tables and actual root/procfs/checkout mount IDs are compared. Freshly opening both again detects changed namespaces or mappings; the resulting mount evidence is checked again when an action proof is used. Only the exact standard autofs/binfmt_misc stack at `/proc/sys/fs/binfmt_misc` is exempt from the critical-overlay veto; no automount is triggered. This common proof is designed for Linux 6.8, 6.14 and 7.0, including dynamic mount-namespace inodes and masked PID-1 namespace links. Synthetic profiles do not claim native execution on those kernels. A filesystem/LSM denial of mountinfo remains a concrete environment blocker. Automatic offline-manager detection is separate and remains conservatively UNKNOWN when its PID-1 namespace reference is masked.

The mount-root field is filesystem-specific: nsfs namespace labels such as `mnt:[4026532668]` are validated and retained verbatim, including namespace type and a bounded positive ASCII inode. They are not filesystem paths or evidence of ownership of another process. Mountpoints remain absolute paths; nsfs is not accepted as the checkout filesystem or a procfs overlay. Every record remains in the complete pinned comparisons and action proof.

A remaining ready registration does not by itself mean that the daemon still executes. Both the process reader and the early stdlib guard classify only that bound historical record as retired when fresh, consistent `/proc/<pid>/stat` observations confirm kernel state Z/X with the matching PID lifetime, boot and namespaces. Stop can then report stopped and an otherwise authorized start can proceed before another parent reaps the zombie. The registration need not be deleted. A retained singleton (including a zombie leader with live threads), unresolved launch or damaged journal still blocks replacement. Do not signal zombies, reap another parent's children or delete journals to force recovery.

Every supported PBCoinData script entry acquires the same checkout singleton before heavy imports and retains it until OS process exit. Fork children close their copy without unlocking the parent. `starting` and `ready` registrations bind the checkout, UID, boot/namespaces, exact process lifetime and guard inode. Readiness also requires the matching launch reservation for a parent-started child. Library imports do not acquire a daemon guard.

Explicit manual actions use request-local authorization under `all-services → pbcoindata`; they do not acquire the controller lease. Stop requires a freshly verified own process and visible namespace/cgroup evidence. Cgroup v1/v2 are parsed by hierarchy, controller lists and complete path components. An ancestor service cgroup alone is not a veto: a guarded direct entry in a scope under the user manager, or a legacy child additionally proven through current local controller ancestry, may be controlled separately. MainPID inequality alone is insufficient. A service MainPID and children of the concrete PBCoinData unit are never signalled through the legacy path. Identity and assignment are checked again before every signal; a change prevents escalation. If the parent ends or changes, origin evidence may become unavailable and the own process remains protected with a concrete diagnosis. The parent unit can still affect a legacy child through its KillMode. Start checks concrete PID, identity, guard, registration, checkout and journal conflicts. Ordinary unrelated foreign Ubuntu services are not globally classified or allowlisted. A hidden process view, shared/network checkout, inaccessible live user manager or contradictory unit evidence still blocks an unsafe start. Missing tools and container/WSL markers alone neither authorize nor prohibit it. Confirmed systemd ownership never falls back to legacy. Restart checks visible start obstacles before stop and authorizes start again after confirmed exit; a later failure reports the actual stopped state.

The versioned private `data/state/pbcoindata-launch.json` document separates `transition` from `pending_launch`. A reservation is atomically synchronized, including directory entries, before Popen. Live/unknown children, missing parent/PID attribution, corrupt journals and identity conflicts block replacement across backoff, clock correction, manual retries and controller changes. Resolution removes only the matching pending entry. Never delete the journal speculatively or use a TTL to unlock it. Historical PID publications can be retired only after checking their bound context and current referenced process. PID reuse by a positively verified unrelated process does not authorize signalling that process. Aliases, hardlinks, inaccessible identities and contradictory metadata remain blocking. Publication cleanup holds the singleton and rechecks bytes, so it cannot delete a newer guarded daemon's files. A boot change never clears a pending launch.

Missing transition evidence does **not alone block manual Start/Stop/Restart**. A successful manual action never certifies transition, UNKNOWN manager ownership, controller authority or automatic retry readiness. Only the legacy IDLE unloading preflight requires independently confirmed transition for this checkout/UID/protocol epoch. Without it, a running legacy idle process remains resident. For confirmed systemd ownership, fresh concrete unit, actual MainPID/lifetime, effective ControlGroup, UID, checkout and guard/ready evidence replaces that legacy attestation. Effective ExecStart, its executable interpreter and an explicitly absolute WorkingDirectory must match the guarded checkout; start restrictions still apply. This never writes legacy transition evidence. Missing transition alone does not block otherwise eligible ACTIVE recovery; current manager, ownership, demand, credentials and start restrictions still apply. Acquiring a guard, publishing ready, old v1 records, current file permissions and a reboot alone do not certify that old unguarded processes are gone.

The local operator-only command is `python starter.py --confirm-coindata-guard-transition --transition-basis legacy-cleanup PBCoinData` (or basis `clean-boot`). It records a separately completed and documented transition: supported autostarts updated to the guarded entry, old unguarded inventory demonstrably cleaned up, and responsible controllers restarted into the current protocol. The clean-boot basis requires a separately authorized clean boot **after** the autostart update. The command performs no cleanup, restart, reboot or remote action and overrides no active guard, identity conflict, pending launch or damaged journal. Use it only after those prerequisites have actually been verified; it is not a routine GUI step. Copied old code and alternative unguarded starters remain an operating boundary, including after a boot if they can run again.

Before automatic unloading, a shared **read-only** preflight checks explicit slave IDLE, enabled healing, current manager/controller, the respective legacy or systemd ownership basis, exact guarded ready identity and readable/executable start dependencies. Missing/unknown credentials do not veto clear IDLE; later ACTIVE still requires ready credentials. Legacy retry content errors are diagnosed without changing bytes or vetoing IDLE; ACTIVE repairs them with a 60-second minimum wait. A valid retry deadline temporarily retains the idle process and is reevaluated automatically. Actual I/O errors or an unusable clock block unloading. Systemd uses its own cooldown/rate policy, without reading the legacy retry file. Structural blockers keep the process idle resident with a reason. No check guarantees future credentials, permissions or an unchanged environment. See the historical records and safe isolated scenarios below; track scoped external validation and environment gaps in the verification protocol.

## Troubleshooting

- **No CMC data yet**: Confirm PBCoinData is running and **Services -> PBCoinData -> Pool** reports at least one active materialized key
- **Mapping stale**: Check `data/logs/PBCoinData.log` for repeated `ERROR` or `self-heal` entries
- **CMC rate-limit errors (429)**: The affected key enters cooldown and the pool tries another eligible key; increase `fetch_interval` if every key remains limited
- **Ignored/approved lists not updating in PBRun**: Verify mapping files exist under `data/coindata/{exchange}/` and restart PBCoinData once

If loading service settings fails, the Settings tab shows the error and a Retry button. Saving remains disabled until the settings load succeeds.
