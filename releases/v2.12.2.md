# v2.12.2

## Cluster outbound peer enforcement

- Explicit **Allowed outbound peers** lists now gate automatic PBCluster SSH
  for master and VPS targets alike, including capability checks, config
  activation and checkpoint coordination. The SSH transport rechecks the current
  policy, local identity and target endpoint immediately before each launch.
- Remove the capability-only SSH exception that contacted unselected masters.
  Skipped nodes no longer accumulate retry warnings from those forbidden probes.
- Stop automatically extending explicit coordinator peer lists after a replica
  joins. An explicit empty list permits no outbound Cluster SSH. Nodes without
  an explicit list retain their role-based defaults; malformed lists and unknown
  or disabled local identities do not regain default access.

## PB8/PB9 readiness on restricted routes

- Optional public capability evidence can travel through already permitted
  connections, such as a shared VPS. Each statement is signed by its originating
  node using its existing key. Publication rechecks current trusted membership,
  signing key, cluster/node identity and the original two-minute expiry.
- Relays cannot forge statements or extend their validity. Missing, expired,
  negative or unverifiable evidence continues to block publication; there is no
  SSH fallback to an unselected node. The existing direct handshake remains
  available on permitted routes with older peers.
- Evidence caches use locked atomic private writes and bounded counts/bytes.
  Optional relay timeouts or malformed replies do not invalidate successful
  direct synchronization. The optional evidence RPC authenticates its sender
  and bounds its input; it does not proxy SSH.

## Rollout and test scope

1. Update a shared, permitted relay VPS and the originating masters first.
2. Then update the restricted publishing master. Allow automatic sync to carry
   the fresh evidence; clocks must be synchronized. Older sources/relays cannot
   supply this new evidence path, so publication can remain blocked until the
   necessary participants have been updated.
3. Check that unselected nodes show topology skips rather than SSH retries and
   test PB8/PB9 saving through the permitted topology.

Capability forwarding does not relay checkpoint coordination: checkpoints with
required but forbidden direct routes remain blocked. Explicit user-operated
setup/repair actions and the separate VPS Monitor are not automatic PBCluster
fanout.

This release is ready for the requested rollout testing. No live remote Cluster
acceptance or host deployment was performed during development/publication.
The experimental PB9 limitations described in v2.12.0 remain in effect; this
patch does not qualify the entire integration for production trading.

## Validation

- **514 focused offline tests passed** on the final implementation: Cluster APIs,
  checkpoints, PB8/PB9 instances, SSH transport, logging/help coverage and real-key
  evidence exchange between two synthetic masters and a shared VPS.
- Regressions cover forbidden/revoked routes, endpoint revalidation, refusal
  before checkpoint RPCs, signature/identity/rotation/expiry, replay, concurrent
  merges, cache byte limits and optional relay failures. The cache-limit test
  failed before its correction.
- Fable reviewed the plan and code. Its concrete edge-case findings were fixed
  and checked again; remaining source-context questions were verified against
  the full implementation. The bounded reviews do not claim a whole-branch audit.
- The test gate selected focused validation. No complete offline suite was run
  again for this patch.
- Final release, help, evidence and topology checks after the version bump:
  **44 passed**. These overlap the implementation checks above.
